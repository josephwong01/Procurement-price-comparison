## 回归中发现并修复的问题

移除履约方案后，定制品和服务类仍需要表达交期及其起算点。本轮新增并经人工审阅精简后的 `offer.commercial_terms`，用于记录：

- 交期天数；
- 交期起算事件；
- 售后；
- 付款条件；
- 报价有效期。

这些字段属于当前供应商报价条件，不用于拆分 Candidate，也不恢复独立履约方案。库存和保修按人工审阅结论暂不纳入本版Schema。

## 业务校验器

已新增 `scripts/validate_product_candidates.py`。四类示例实跑结果为 `PASSED`，并通过六项反向测试：错误权重、错误总分、缺失证据、排除原因缺失、未验证候选提前排名、Candidate ID重复均能被拦截。

## 交期区间人工审核修订

蓝牙音响真实回归后，交期结构已通过人工审核并完成修订：

- 使用 `min_days`/`max_days` 表达固定值、区间或仅上限；
- 增加 `day_type` 区分自然日、工作日和未知口径；
- 增加 `scope` 区分生产、发货、最终交付和服务交付；
- `start_event` 与 Requirement Schema 枚举对齐；
- 完全未知必须使用 `lead_time=null`，交期对象不得上下限同时为空；
- 业务校验器强制最短天数不得大于最长天数。

四类示例与两条真实蓝牙音响候选共6份记录重新校验为 `PASSED`。上下限同时为空、非法天数口径、非法范围、旧起算事件值和反向区间五项负向测试均被正确拦截。

## 定制品与服务类轻量真实回归

按人工决定跳过询盘后，新增1688人偶服和淘宝住宅设计服务各一条真实页面候选。两条记录均保持 `PENDING_VALIDATION`，入口价不作为正式报价，未知的材料、完整服务范围、交期和费用不作默认假设。

四类示例及四条真实候选共8份记录重新运行业务校验，结果为 `PASSED`。本轮没有发送商家消息，也没有取得或伪造正式报价。
